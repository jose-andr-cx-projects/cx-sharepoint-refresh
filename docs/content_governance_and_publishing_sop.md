# CX Content Governance and Publishing SOP

**Status:** CX proposed operating standard — working draft for validation and handover  
**Updated:** 11 November 2026  
**Scope:** Refreshed CX pages on the Purple CoMWeb site; linked CX resources in the existing Intranet Documents library  
**Authority:** Does not replace CoMWeb / Digital governance, permissions, or the authorised publishing workflow

## 1. Purpose and principles

Provide a minimum useful process for creating, updating, reviewing, publishing, maintaining and retiring CX intranet content after the SharePoint refresh. The branch owns content accuracy and employee relevance; authorised CoMWeb roles control publication and restricted administrative actions.

Principles:
- **Employee need first:** structure content around what an employee needs to do.
- **One authoritative source:** link to maintained information rather than duplicate it.
- **A named editor and accountable team:** every CX page has someone to maintain it.
- **Use existing SharePoint fields and workflows:** avoid parallel approval processes or new columns without demonstrated need.
- **Publish, validate, maintain:** published does not automatically mean current or findable.
- **Minimum useful governance:** ownership, checks, review triggers and retirement pathways; no new approval bottleneck.

## 3. Site Pages metadata: existing fields first

**Platform mandatory according to the CoMWeb Editor Training Manual:** Name, Content Editor, Division and Branch.  
**Additional CX operating minimum:** Team and Description, where supported in the existing Page Details/configuration.

| Field | CX rule | Entry / handling |
|---|---|---|
| Name / title | **Required** | Exact approved employee-facing page title; check page URL before publishing |
| Division | **Required by CoMWeb manual** | Select approved existing organisation value; do not invent a new value |
| Branch | **Required by CoMWeb manual** | Customer Experience, if this is the existing approved choice |
| Content Editor | **Required by CoMWeb manual** | Named person who edits page content and metadata; not necessarily the accountable business owner |
| Team | **CX operating standard** | Single accountable team, using an existing choice/value if available; cross-team contributors do not create duplicate owners |
| Description | **CX operating standard** | One or two plain-language sentences: who the page helps and what employees can do there |
| Keywords | Useful supporting metadata | Employee language, synonyms, acronyms; reuse existing field if present |
| Related Topic | Optional | Reuse established taxonomy choices; avoid one new category per CX page |
| Display order | Conditional | Set only if an existing navigation/view consumes it |
| Stage / Status | Workflow | Follow CoMWeb workflow and current stage values; do not independently invent statuses |
| Review Date / Next review | Workflow / lifecycle | Follow current rules; manual describes next review as 12 months after publication but confirm automation |
| Reviewed by, Published by, Publish Date, Publisher comments | Workflow evidence | Maintain through the established review/publish process |
| Reviewer, Publishers, Intranet Owner | Permissions / routing | Follow existing organisational roles, not a CX-created permission model |

Do not make all supporting fields mandatory without confirming whether the platform supports them and whether they add value. **The branch's key control is named accountability, not new metadata.**

## 4. Document library and CoMpanion discovery

Use the **existing Intranet Documents library** and the **Customer Experience Intranet Document Set** if present and suitable. Proposed operating arrangement: keep documents directly in that set, without CX subfolders initially. This is a **proposed configuration**, not a technical confirmation.

For document-level discoverability, prioritise existing fields:
- **Name:** understandable document title.
- **Description:** explain what the file helps employees do and when to use it.
- **Keywords:** everyday search language, synonyms and recognised acronyms.
- **Resource Type:** choose from existing approved values.
- **Division and Branch:** use existing Document Set shared/inherited metadata, subject to validation.
- **Content Type / Modified:** retain existing system behaviour.

Do not create new Topic, Owner or Status columns for go-live unless a real governance or retrieval gap is demonstrated.

CoMpanion's indexing, knowledge-source scope, permissions and retrieval of metadata must be confirmed with its administrator. Metadata alone does not guarantee results. Use the separate CX knowledge navigation document for page-offer mapping, employee questions, URLs and authoritative-source relationships; avoid copying that mapping into extra Site Pages columns.

## 5. Roles and decision rights

| Role/function | Accountability | Permissions boundary |
|---|---|---|
| Accountable CX team / business owner | Confirms purpose, accuracy, currency and authoritative sources; decides whether content is needed | Not automatically a SharePoint publisher |
| Named Content Editor | Maintains copy, page fields, links, accessibility and the next review prompt | May prepare and submit drafts; normal page creation/publication/archive restrictions remain |
| SME / Reviewer | Checks technical or policy content where risk or change warrants review | CoMWeb Request Review is optional in the documented general workflow; CX can require accuracy sign-off for specified changes |
| CoMWeb Publisher | Handles publication through existing approval and notification process | Must hold existing publisher permissions |
| Intranet Owner | Coordinates creation, archival and restricted administrative changes | Existing CoMWeb authority; no delegated powers implied |
| CX publishing coordinator (existing function, not new position) | Holds seven-page ownership/URL map, monitors review due dates, coordinates cross-page issues and handover | Does not create a second approval gate |

A content editor and accountable team may be different. If ownership is shared, record one accountable team and identify contributing SMEs in the working register.

## 6. SOP workflow

### A — Request and triage
1. Identify change trigger: new employee need, accuracy correction, source update, link change, accessibility issue or scheduled review.
2. Check whether an authoritative source already exists. Prefer a maintained link to duplicated content.
3. Decide the smallest action: **keep / update / link / create / retire**.
4. Confirm accountable team, named Content Editor and relevant SMEs.

### B — Prepare
1. Edit the existing draft/page in the authorised SharePoint environment.
2. Apply agreed title, description, mandatory metadata, team assignment and useful search keywords.
3. Check employee-focused wording, headings, accessibility, links, attachments and page placement.
4. Ensure linked documents are authoritative and have clear file descriptions/keywords where relevant.
5. Record material link dependencies when URLs are changing.

### C — Review and approval
1. Obtain accountable team/SME accuracy agreement for new, materially changed, policy-sensitive or cross-team content.
2. Follow current **Request Review** steps where required; reviewers may accept or return for changes.
3. Use the existing **Notify Publisher** workflow with a concise summary of what changed. Do not replace this with Teams approval unless explicitly authorised.
4. Publisher acts through current CoMWeb workflow. Archive/create requests go to the authorised Intranet Owner, with Service Hub routing where current practice requires it.

### D — Publish and verify
1. Confirm the published page opens for the intended audience.
2. Verify expected content, working links, page navigation, anchors and accessibility.
3. Check the destination and content exposed by CoMpanion only where the configured knowledge source includes the page/resource.
4. Confirm publishing evidence is recorded through SharePoint fields.
5. Record defects and the person responsible for correction; do not declare completion with launch-critical failures outstanding.

### E — Maintain and review
1. Follow the platform's configured review date; also trigger review when policy, services, ownership, files or links change.
2. Named editor checks content; accountable team confirms accuracy.
3. Update in place where feasible. Reuse the established review/notify/publish route.
4. Where owner or source cannot be confirmed, flag the content for decision rather than leaving it unowned.

### F — Retire or replace
1. Identify old URL, new URL, source owner and affected inbound references.
2. Because the refreshed Purple pages have **new URLs** and CoMWeb redirects were reported unavailable, check cross-site references before retiring old Purple pages.
3. The Green and Black pages remain published at the 18 November go-live; their decommissioning is a separate post-go-live stream. Any retained links to archived Purple pages still need updating.
4. Confirm publish-versus-archive timing and permissions with the Intranet Owner/Jenny.
5. Verify retired pages and documents no longer appear in CoMpanion where this is required and technically supported.
6. Keep the URL mapping and decision evidence; archive only through authorised workflow.

## 7. Minimum publish checklist (copy-ready)

- [ ] Employee need and authoritative source confirmed
- [ ] Accountable CX team confirmed
- [ ] Named Content Editor assigned
- [ ] Name, Division, Branch and other required Page Details complete
- [ ] Description states who the page helps and what it offers
- [ ] Team, Keywords and Related Topic populated where appropriate/available
- [ ] Content fact-checked and accessible; links/attachments tested
- [ ] SME accuracy sign-off obtained if required
- [ ] Existing SharePoint review / Notify Publisher steps completed
- [ ] Published URL, navigation, anchors and important inbound pathways checked
- [ ] Review date/trigger and maintenance responsibility confirmed

## 8. Working register: minimum fields outside the platform

Only hold what SharePoint does not already give us or what a cross-page cutover requires:
**Page title | page URL | accountable team | named editor | authoritative source / key dependencies | next review trigger | exceptions/action owner**.

Use existing SharePoint page metadata for publication records. Keep Jira for tracked work and Confluence/approved records for formal decisions. Avoid a duplicate CX publishing database.
